# Bug Report: 预支付接口订单状态校验因枚举类型比较错误导致所有订单都返回"已支付"

**Bug ID**: BUG-PAY-STATUS-001  
**标题**: `POST /v1/pay/pre_order` 因订单状态与枚举对象直接比较，导致任意状态的订单均返回"订单已支付"  
**模块**: 订单系统 / 支付 / 预支付校验  
**严重级别**: 高  
**优先级**: P0  
**状态**: 已修复  
**发现日期**: 2026-06-11  
**提交人**: 测试团队 1号

---

## 一、问题概述

调用预支付接口 `POST /v1/pay/pre_order` 时，即使订单处于未支付状态（`order_status = 1`），接口也会返回"订单已支付"错误，导致用户无法对任何订单发起支付。

经定位，问题发生在支付服务的订单状态校验逻辑中。代码将数据库中存储的整数类型订单状态与 Python 枚举对象直接比较，两者类型不同，比较结果永远为 `True`，因此无论订单实际状态为何值，都会进入"已支付"分支。

- 用户无法完成支付，阻断购物核心链路
- 支付前库存二次校验无法执行
- 测试用例 `TC-ORDER-004` 无法通过

## 六、预期结果

当订单 `order_status = 1`（未支付）时，接口应通过状态校验，继续执行支付前库存检测和微信预支付下单流程，不应返回"订单已支付"错误。

只有当订单状态为 `2`（已支付）、`3`（已发货）、`4`（已支付但库存不足）等已完成支付的状态时，才应拒绝并提示"订单已支付"。

---

## 七、根因分析

### 1. 现象分析

该问题不是订单不存在、用户不匹配或网络问题导致的，因为接口已通过订单存在性校验和用户匹配校验后才触发此错误。

问题发生在第三步订单状态校验时，与 Python 枚举类型比较机制有关。

### 2. 关键代码 / 关键逻辑

`app/service/pay.py` 中的订单状态校验代码（修复前）：

```python
if order.order_status != OrderStatusEnum.UNPAID:
    raise OrderException(
        msg='订单已支付',
        error_code=8003,
        code=404
    )
```

`order.order_status` 是从数据库读取的整数字段，值为 `1`。

`OrderStatusEnum.UNPAID` 是 Python `Enum` 枚举对象，而不是整数：

```python
class OrderStatusEnum(Enum):
    UNPAID = 1  # 待支付
    PAID = 2    # 已支付
    ...
```

Python 中整数与枚举对象比较时，两者类型不同，即使数值相同也不相等：

```python
>>> 1 == OrderStatusEnum.UNPAID
False
>>> 1 != OrderStatusEnum.UNPAID
True
```

因此，无论 `order.order_status` 的实际值是 `0`、`1`、`2` 还是任何值，条件 `order.order_status != OrderStatusEnum.UNPAID` 始终为 `True`，永远都会抛出"订单已支付"异常。

### 3. 根因结论

问题根因是订单状态校验时将整数类型的 `order.order_status` 与 `Enum` 枚举对象直接比较，Python 中整数与枚举对象不相等，导致比较结果恒为 `True`，所有订单均被误判为已支付。

---

## 八、修复方案

### 当前采取的修复策略

已将枚举对象改为与其整数值 `.value` 进行比较。

修复前：

```python
if order.order_status != OrderStatusEnum.UNPAID:
```

修复后：

```python
if order.order_status != OrderStatusEnum.UNPAID.value:
```

### 后续推荐优化方向
- 对项目中所有枚举比较逻辑进行排查，确认是否存在其他地方同样用枚举对象与整数直接比较。
- 考虑在 `Order` 模型中封装状态判断属性，例如 `order.is_unpaid`，从根本上避免外部直接比较状态值。
- 增加枚举状态的单元测试，覆盖各状态流转校验逻辑。

---

## 九、修复结果

当前问题已修复，状态校验改为比较枚举值。

修复后使用 `order_status = 1` 的未支付订单调用 `POST /v1/pay/pre_order`，不再被误判为已支付，可正常进入支付流程。

## 十五、结论

该问题属于枚举类型误用导致的订单状态校验恒为"已支付"的高优先级缺陷，已定位并修复。修复前会导致所有订单均无法进入支付流程；修复后状态校验恢复正常。建议同时排查项目其他枚举比较逻辑，避免同类问题影响订单状态流转。
