# Bug Report: 用户账号绑定与解绑接口返回服务器端异常

**Bug ID**: BUG-USER-IDENTITY-001  
**标题**: `/v1/user/bind` 与 `/v1/user/unbind` 在操作站内账号身份时返回服务器端异常  
**模块**: 用户中心 / 账号绑定 / 账号解绑  
**严重级别**: 高  
**优先级**: P1  
**状态**: 已修复  
**发现日期**: 2026-06-11  
**提交人**: 测试团队 1号

---

## 一、问题概述

调用用户账号绑定接口 `PUT /v1/user/bind` 或账号解绑接口 `PUT /v1/user/unbind` 时，系统返回 `服务器端异常`，导致用户无法正常绑定或解绑邮箱、用户名、手机号等登录身份。

该问题发生在项目已将登录身份信息迁移到 `identity` 表之后，但部分绑定 / 解绑逻辑仍沿用旧的数据结构，尝试直接修改 `User.email`、`User.username`、`User.mobile` 等只读属性，最终触发运行时异常。

---

## 二、影响范围

### 受影响功能
- 用户账号绑定
- 用户账号解绑
- 邮箱 / 用户名 / 手机号等站内登录身份维护
- 用户资料与登录身份一致性维护

### 受影响接口 / 页面
- `PUT /v1/user/bind`
- `PUT /v1/user/unbind`

### 业务影响
- 用户无法正常绑定新的邮箱、用户名或手机号身份
- 用户无法正常解绑已有登录身份
- 接口返回通用 `服务器端异常`，错误信息不可读，不利于前端展示和问题定位
- 影响账号安全相关功能的可用性与回归测试稳定性

## 六、预期结果

### 绑定接口

当请求参数合法，且账号未被其他用户绑定时，`PUT /v1/user/bind` 应正常创建对应 `identity` 记录，并返回成功，例如：

```json
{
  "error_code": 1,
  "msg": "创建 | 更新成功",
  "data": null
}
```

### 解绑接口

当用户至少保留一种登录身份时，`PUT /v1/user/unbind` 应删除对应 `identity` 记录，并返回成功。

当解绑后会导致用户没有任何登录方式时，应返回明确业务错误，例如 `无法解绑，至少保留一种登录方式`，不应返回服务器端异常。

---

## 七、根因分析

### 1. 现象分析

该问题不是 token 无效或权限不足导致的鉴权问题，因为请求已经通过 `@auth.login_required` 获取到当前用户后，才进入绑定 / 解绑业务逻辑。

异常发生在 `IdentityDao` 对用户登录身份进行创建或删除时。

### 2. 关键代码 / 关键逻辑

项目当前的用户模型中，`User.email`、`User.username`、`User.mobile` 是通过 `Identity` 表查询出来的只读属性，不是 `user` 表中的可写字段。

旧版绑定逻辑在创建站内身份时仍执行类似逻辑：

```python
attr = ClientTypeEnum(type).name.lower()
setattr(user, attr, identifier)
```

旧版解绑逻辑在删除站内身份时仍执行类似逻辑：

```python
attr = ClientTypeEnum(type).name.lower()
setattr(user, attr, None)
```

由于 `User.email`、`User.username`、`User.mobile` 没有 setter，因此会触发 `AttributeError: can't set attribute`，最终被统一异常处理包装为：

```json
{
  "error_code": 999,
  "msg": "服务器端异常"
}
```

### 3. 根因结论

问题根因是用户登录身份数据模型已迁移到 `identity` 表，但 `IdentityDao.bind` / `IdentityDao.unbind` 仍保留旧版直接修改 `User` 只读属性的逻辑，导致运行时异常。

---

## 八、修复方案

### 当前采取的修复策略
- 移除绑定逻辑中对 `User.email`、`User.username`、`User.mobile` 等只读属性的写入。
- 移除解绑逻辑中对 `User.email`、`User.username`、`User.mobile` 等只读属性的清空操作。
- 绑定和解绑统一只操作 `identity` 表。
- 绑定站内账号时，复用当前用户已有的密码凭证，避免新绑定的邮箱 / 手机号 / 用户名无法通过密码登录。
- 修复 `get_credential` 在没有可用密码凭证时可能因解包 `None` 导致服务器异常的问题。

### 后续推荐优化方向
- 对重复绑定已存在 `identifier` 的场景增加业务异常提示。
- 对已绑定同类型身份的重复绑定行为增加明确规则，例如覆盖、拒绝或先解绑再绑定。
- 为绑定 / 解绑接口增加参数校验器，避免直接使用未校验的 `get_request_args()`。
- 为 `IdentityDao` 增加单元测试，覆盖用户名、邮箱、手机号、微信 openid 等多类型身份。

---

## 九、修复结果

当前问题已修复，`IdentityDao` 的绑定与解绑逻辑已改为只操作 `identity` 表，不再写入 `User` 模型中的只读属性。

修复后预期：

- `PUT /v1/user/bind` 不再因 `can't set attribute` 返回服务器端异常。
- `PUT /v1/user/unbind` 不再因 `can't set attribute` 返回服务器端异常。
- 用户身份数据仍保持在 `identity` 表中，与当前模型设计一致。

---

## 十、建议

1. 统一用户身份数据模型，明确 `User` 表只保存基础资料，登录身份全部由 `Identity` 表维护。  
2. 禁止业务代码直接写入 `User.email`、`User.username`、`User.mobile` 这类只读属性。  
3. 为重复绑定、解绑不存在身份、解绑最后一种身份等边界场景补充明确业务错误码。  
4. 为 `PUT /v1/user/bind` 和 `PUT /v1/user/unbind` 补充自动化回归测试。  
5. 检查其他模块是否仍存在类似 `setattr(user, attr, ...)` 的旧版身份写入逻辑。

## 十五、结论

该问题属于用户身份模型迁移后遗留逻辑未同步改造导致的功能缺陷，已定位并完成修复。当前绑定和解绑逻辑已统一改为操作 `identity` 表，建议后续继续补充重复绑定、最后一种身份解绑等边界场景的业务异常处理和自动化测试。
