# Bug Report: 删除后重新注册同名账号触发服务器端异常

**Bug ID**: BUG-USER-REGISTER-REUSE-001  
**标题**: 账号删除后再次注册与旧账号同名时返回 1007 服务器端异常  
**模块**: 用户管理 / 账号注册  
**严重级别**: 高  
**优先级**: P1  
**状态**: 初修复  
**发现日期**: 2026-06-12  
**提交人**: 1号

---

## 一、问题概述

当一个账号已经被删除后，用户再次使用与旧账号相同的身份信息进行注册时，接口没有返回明确的业务提示，而是直接返回 `1007` 服务器端异常。

当前现象说明：系统在“删除后重注册同名账号”的场景下，未能正确处理软删除后的身份标识复用或冲突校验，导致注册流程抛出内部异常。

---

## 二、影响范围

### 受影响功能
- 用户注册
- 删除后账号恢复 / 复用
- 账号唯一性校验

### 受影响接口 / 页面
- `POST /v1/user`
- `DELETE /v1/user`

### 业务影响
- 用户删除账号后无法再次使用相同身份信息注册
- 注册流程抛出内部错误，影响用户体验
- 软删除账号复用逻辑不完整，存在数据一致性风险

---

## 三、复现环境

- 项目：`mini-shop-server`
- 环境：`本地开发`
- 服务地址：`http://127.0.0.1:5000`
- 数据库：开发环境 MySQL
- 测试数据：`fake.py` 初始化账号数据
- 测试接口：`POST /v1/user`

---

## 四、复现步骤

### 步骤 1：删除已有账号
调用 `DELETE /v1/user` 删除当前账号，相关 `user` 与 `identity` 记录进入软删除状态。

### 步骤 2：重新注册相同账号信息
再次调用 `POST /v1/user`，提交与旧账号相同的用户名 / 手机号 / 邮箱中的部分或全部信息。

### 步骤 3：观察结果
接口返回 `1007` 服务器端异常，而不是正常注册成功或明确的业务冲突提示。

---

## 五、实际结果

接口返回如下错误：

```json
{
  "error_code": 1007,
  "msg": "The server encountered an internal error and was unable to complete your request. Either the server is overloaded or there is an error in the application.",
  "request_url": "POST /v1/user"
}
```

在排查过程中，数据库层还出现过如下异常：

```text
pymysql.err.IntegrityError: (1062, "Duplicate entry 'user' for key 'identity.identifier'")
```

---

## 六、预期结果

当用户删除后再次注册时，系统应满足以下之一：

1. 如果业务允许复用软删除账号，则应自动恢复对应账号，并返回注册成功；
2. 如果业务不允许复用，则应返回明确的业务错误，例如“用户名已存在”或“账号已被占用”；
3. 无论哪种策略，都不应返回服务器端内部异常 `1007`。

---

## 七、根因分析

### 1. 现象分析
问题集中在“删除后再次注册同名账号”场景。系统对软删除数据的处理与注册流程不一致，导致唯一标识冲突时抛出数据库异常。

### 2. 关键代码 / 关键逻辑

#### `app/models/identity.py`
```python
identifier = Column(String(100), unique=True, comment='标识(手机号、邮箱、用户名或第三方应用的唯一标识)')
```

`identity.identifier` 具有唯一约束。软删除后如果旧记录仍保留，注册时仍可能发生冲突。

#### `app/core/db.py`
```python
def delete(self, commit: bool = True):
    '''软删除'''
    self.delete_time = int(round(datetime.now().timestamp()))
    self.save()
```

项目采用软删除机制，删除后记录仍存在于数据库中，只是 `delete_time` 被设置为当前时间。

#### `app/dao/user.py`
注册流程在创建 `identity` 时直接执行唯一性校验并创建新记录，若未正确识别软删除场景，就会触发唯一键冲突。

### 3. 根因结论
根因是：**软删除账号在注册时没有被正确识别为可复用或需排除的历史数据，导致 `identity.identifier` 唯一约束冲突，并最终被包装成服务器端异常。**

---

## 八、修复方案

### 当前采取的修复策略
- 明确“删除后重注册”的业务规则
- 对软删除账号增加复用判断
- 当用户名 + 手机号，或用户名 + 邮箱，或三者都匹配时，允许复用同一个软删除账号
- 若不满足复用条件，则按普通注册冲突逻辑处理，并返回明确业务错误

### 后续推荐优化方向
- 注册流程增加软删除数据识别与复用机制
- 统一 `user` / `identity` 的删除与恢复规则
- 对数据库唯一约束冲突增加业务级异常转换，避免内部错误直接暴露给前端
- 为删除后重注册场景补充自动化回归测试
