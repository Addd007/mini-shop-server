# Bug Report: 登录时 identity 存在但 user 被删除返回服务器端异常

**Bug ID**: BUG-AUTH-USER-DELETED-001  
**标题**: `POST /v1/token` 当 identity 存在但对应 user 被删除时返回服务器端异常  
**模块**: 认证鉴权 / 登录数据一致性校验  
**严重级别**: 中  
**优先级**: P1  
**状态**: 已修复  
**发现日期**: 2026-06-11  
**提交人**: 测试团队 1号

---

## 一、问题概述

调用登录接口 `POST /v1/token` 时，如果 `identity` 表中存在对应账号记录，但 `user` 表中的用户记录已被删除，接口返回 `服务器端异常`。

该问题属于数据一致性边界场景的异常处理缺失。当出现数据不一致时，应返回明确的业务错误提示（如「用户不存在」），而不是服务端异常。当前表现会误导调用方认为后端服务异常，不利于问题定位。

## 七、根因分析

### 1. 现象分析

该问题发生在 `identity` 表存在记录、但 `user` 表中对应用户已被删除的场景。

### 2. 关键代码 / 关键逻辑

修复前，`LoginVerifyService.verify_by_username` 中对 `User.get()` 返回值未做空值检查：

```python
@staticmethod
def verify_by_username(username, password):
    identity = Identity.get_or_404(identifier=username, type=ClientTypeEnum.USERNAME.value,
                                   e=IdentityException(msg='该用户名未注册'))
    if identity.identifier != username:
        raise IdentityException(msg='该用户名未注册')
    identity.check_password(password, e=AuthFailed(msg='密码错误'))
    user = User.get(id=identity.user_id)
    return {'uid': user.id, 'scope': user.auth_scope}  # user 为 None 时报错
```

当 `User.get(id=identity.user_id)` 返回 `None` 时，后续访问 `user.id` 会抛出 Python 原生 `AttributeError`，被全局异常处理捕获后返回「服务器端异常」。

`verify_by_email` 和 `verify_by_mobile` 存在同样的问题。

### 3. 根因结论

问题根因是登录验证逻辑中对 `User.get()` 返回值缺少空值检查，导致数据不一致场景下的 `AttributeError` 被误处理为服务端异常。

---

## 八、修复方案

### 当前采取的修复策略

在 `verify_by_username`、`verify_by_email`、`verify_by_mobile` 三个方法中，对 `User.get()` 返回值增加空值检查。

修复前：

```python
user = User.get(id=identity.user_id)
return {'uid': user.id, 'scope': user.auth_scope}
```

修复后：

```python
user = User.get(id=identity.user_id)
if not user:
    raise UserNotFound(msg='用户不存在')
return {'uid': user.id, 'scope': user.auth_scope}
```

同时在文件头部增加 `UserNotFound` 异常类的引入：

```python
from app.libs.error_code import AuthFailed, IdentityException, UserNotFound
```

### 后续推荐优化方向
- 对所有涉及跨表关联查询的场景进行排查，确保关联数据缺失时有明确的业务错误提示。
- 考虑在删除 `user` 时级联删除或软删除对应的 `identity` 记录，从根本上避免数据不一致。
- 为数据不一致场景补充自动化测试。

## 十、建议

1. 为登录接口补充数据不一致场景的测试用例。
2. 排查其他跨表关联查询是否存在同类空值检查缺失问题。
3. 考虑在业务层面保证 `user` 和 `identity` 数据的一致性（级联删除或软删除）。
4. 避免原生 `AttributeError`、`TypeError` 等异常直接穿透为「服务器端异常」。

### 待讨论：场景 3（两个表都删除）的返回语义

当前修复仅覆盖场景 2（只删 `user`）。场景 3（`identity` 和 `user` 都删除）目前返回「该用户名未注册」，因为登录流程先查 `identity` 表，找不到就直接抛出 `IdentityException`。

从语义上看，「该用户名未注册」暗示该用户名可以用于注册新账号，但「用户不存在」暗示该账号曾经存在但已被删除。两个表都删除时，用户确实曾经存在过，返回「用户不存在」可能更准确。

但从技术实现角度，当 `identity` 都不存在时，系统已经无法得知该用户名是否曾经注册过（无法关联到 `user_id`），因此无法区分「从未注册过」和「注册后被完全删除」。

如需统一为「用户不存在」，可能的方案：
- 方案 A：在 `user` 表中保留软删除记录，`identity` 删除后仍可通过其他方式（如用户名字段）反查。但当前 `user` 表没有存储用户名，用户名存在 `identity` 表中。
- 方案 B：删除用户时只做软删除，不真正删除 `identity` 和 `user` 记录。
- 方案 C：接受现状，认为两个表都删除后系统内已无该用户痕迹，返回「未注册」从系统视角是事实。

**建议后续与开发讨论确认预期行为后再决定是否需要额外处理。**
