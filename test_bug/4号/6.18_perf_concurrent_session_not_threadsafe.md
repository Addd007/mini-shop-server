# Bug Report: 并发性能测试中 Session 对象多线程共享，非线程安全

**Bug ID**: BUG-PERF-SESSION-THREAD-001  
**标题**: `_concurrent_request` 在多线程中共享 `ApiClient` 的 `requests.Session()`，可能导致连接池竞争和偶发失败  
**模块**: 性能测试 / 并发测试  
**严重级别**: 中  
**优先级**: P2  
**状态**: 已定位  
**发现日期**: 2026-06-18  
**提交人**: 测试团队 4号

---

## 一、问题概述

4号性能测试中，`test_concurrent_login` 和 `test_concurrent_query` 使用 `_concurrent_request()` 函数在线程池中并发发送请求。该函数通过同一个 `ApiClient` 实例的 `requests.Session()` 发送所有请求，但 `requests.Session` 的连接池适配器（`HTTPAdapter`）在多线程环境下并非完全线程安全，可能导致连接池竞争、连接泄漏或偶发的请求失败。

## 四、复现步骤

### 步骤 1：查看 `_concurrent_request` 实现

```python
def _concurrent_request(client, method, url, json_data, concurrency, timeout=30):
    results = []
    errors = []
    lock = threading.Lock()
    
    def worker():
        try:
            # 所有线程共享同一个 client.session
            resp = client.request(method, url, json=json_data, timeout=timeout)
            with lock:
                results.append(resp)
        except Exception as e:
            with lock:
                errors.append(str(e))
    
    with ThreadPoolExecutor(max_workers=concurrency) as executor:
        futures = [executor.submit(worker) for _ in range(concurrency)]
        for f in futures:
            f.result(timeout=timeout + 5)
    
    return results, errors
```

### 步骤 2：查看 `ApiClient` 的 Session 使用

```python
class ApiClient:
    def __init__(self, base_url, token=None):
        self.base_url = base_url
        self.session = requests.Session()  # 单例 Session
        if token:
            self.session.headers.update({"Authorization": f"Bearer {token}"})
```

### 步骤 3：运行高并发测试

在高并发（20+）时，共享 `Session` 的连接池可能出现竞争，导致部分请求失败。

---

## 五、实际结果

`requests.Session` 的连接池在 `urllib3` 层面有基本线程安全保护，但 `Session` 对象本身的状态（如 cookie、header 修改）在多线程写入时不是线程安全的。并发测试中可能出现：
- `Connection pool is full, discarding connection` 警告
- 偶发 `ConnectionError` 或 `ReadTimeout`
- 响应结果交叉污染（极少情况）

---

## 六、预期结果

并发测试应为每个线程创建独立的 `requests.Session()` 或无状态的请求方式，避免 Session 状态在多线程间共享。

---

## 七、根因分析

### 1. 现象分析

`ApiClient` 的设计初衷是维护单个 Session 以复用连接，但在并发测试场景下，多线程共享 Session 会带来线程安全问题。

### 2. 关键代码

```python
# ApiClient 使用单一 Session
self.session = requests.Session()

# _concurrent_request 中所有线程使用同一 client
resp = client.request(method, url, json=json_data, timeout=timeout)
```

### 3. 根因结论

并发测试框架设计时未考虑 `requests.Session` 的线程安全性，使用了不适合高并发共享的 Session 对象。

---

## 八、修复方案

### 推荐修复

方案一：在 `_concurrent_request` 中为每个线程创建独立 Session：

```python
def worker():
    try:
        s = requests.Session()
        if client.token:
            s.headers.update({"Authorization": f"Bearer {client.token}"})
        url = f"{client.base_url}{path}"
        resp = s.request(method, url, json=json_data, timeout=timeout)
        with lock:
            results.append(resp)
    except Exception as e:
        with lock:
            errors.append(str(e))
```

方案二：使用 `requests` 的无 Session 模式（每次独立请求）：

```python
resp = requests.request(method, url, json=json_data, 
                        headers=headers, timeout=timeout)
```

### 后续推荐
- 对性能测试框架进行压力验证，确保在高并发（100+）下稳定运行
- 在 `_concurrent_request` 中增加连接池大小配置
- 增加重试机制处理偶发网络错误

## 十、建议

1. 并发测试中每个线程应使用独立的 HTTP 连接或 Session
2. 将并发请求工具函数独立为公共模块，供各测试模块复用
3. 增加并发测试的稳定性断言：不仅验证成功率，还应验证错误类型
4. 考虑使用 `aiohttp` 或 `httpx` 的异步客户端替代多线程方案

## 十三、结论

该问题属于测试框架设计缺陷，并发测试中多线程共享 `requests.Session` 可能导致偶发失败和测试结果不稳定。虽然 `requests` 库的连接池有一定线程安全保护，但 Session 状态共享在高并发下仍存在风险，建议为每个线程创建独立 Session 或使用无状态请求方式。
