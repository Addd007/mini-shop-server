# Bug Report: 日志审计测试 TC-LOG-011 断言过弱，无法验证"不产生成功登录日志"

**Bug ID**: BUG-LOG-AUDIT-ASSERT-001  
**标题**: `test_log_audit` 中 `check_login_log_fail` 分支仅断言 `items is not None`，无法验证密码错误时不产生**成功**登录日志  
**模块**: 日志审计 / 自动化测试  
**严重级别**: 中  
**优先级**: P2  
**状态**: 已定位  
**发现日期**: 2026-06-18  
**提交人**: 测试团队 4号

---

## 一、问题概述

4号日志审计测试中，TC-LOG-011 的意图是验证"密码错误登录不会在登录日志中产生成功记录"。但 `test_log_audit` 函数中 `check_login_log_fail` 分支的断言仅为 `assert items is not None`，只验证了"日志表存在记录"，而没有验证"记录中不包含成功状态的条目"。这意味着即使密码错误被错误地记录为成功登录，测试仍然会 PASS。

---

## 二、影响范围

### 受影响功能
- 登录日志审计
- 登录失败记录验证
- 自动化测试有效性

### 受影响接口
- `POST /v1/token`（登录）
- `GET /cms/log/login`（登录日志查询）

### 业务影响
- 无法通过自动化测试发现"失败登录被误记为成功"的缺陷
- 审计日志数据准确性无法保障
- 安全审计依赖的日志可能包含错误数据

---

## 三、复现环境

- 项目：`mini-shop-server`
- 环境：本地开发环境
- 服务地址：`http://127.0.0.1:5000`
- 测试文件：`tests/api/4号/test_log_cases.py`

---

## 四、复现步骤

### 步骤 1：查看 `check_login_log_fail` 分支

```python
if case_id == "TC-LOG-011":
    # 密码错误登录
    resp = client.request("POST", "/v1/token", json={
        "account": test_account,
        "secret": "wrong_password",
        "type": 100
    })
    assert resp.status_code == 200  # 接口返回200但登录失败
    body = resp.json()
    assert body.get("error_code") != 0  # 登录确实失败
    
    # 查询登录日志
    resp2 = auth_client.request("GET", "/cms/log/login", params={"page": 1, "size": 20})
    items = resp2.json().get("data", {}).get("items", [])
    assert items is not None  # ← 断言过弱
```

### 步骤 2：分析断言强度

`assert items is not None` 只验证了 `items` 字段存在（不为 `None`），但即使 `items` 中包含一条 `status: "success"` 的记录，测试也会通过。

### 步骤 3：对比预期行为

TC-LOG-011 的预期是：密码错误时登录日志中不应产生"成功"记录，即所有记录的 `status` 不应为 `success`（或等价字段）。

---

## 五、实际结果

断言 `items is not None` 无法验证登录日志内容的正确性。

---

## 六、预期结果

应验证查询到的登录日志中，不存在对应测试账号在失败时刻产生的成功状态记录。例如：

```python
# 检查最近一条日志是否为失败状态
recent_logs = [item for item in items if item.get("account") == test_account]
if recent_logs:
    latest = recent_logs[0]
    assert latest.get("status") != "success", \
        f"密码错误登录被错误记录为成功: {latest}"
```

或更严格地验证"该时间段内无成功记录"。

---

## 七、根因分析

### 1. 现象分析

断言只检查了 API 响应结构完整性，未验证日志内容的业务语义正确性。

### 2. 关键代码

```python
# tests/api/4号/test_log_cases.py
assert items is not None
# 缺少对 items 内容的验证
```

### 3. 根因结论

测试断言只做了结构校验，遗漏了业务语义校验，属于测试覆盖深度不足。

---

## 八、修复方案

### 推荐修复

```python
if case_id == "TC-LOG-011":
    # ... 密码错误登录 ...
    resp2 = auth_client.request("GET", "/cms/log/login", params={"page": 1, "size": 20})
    data = resp2.json().get("data", {})
    items = data.get("items", [])
    assert items is not None
    
    # 验证最近一条该账号的日志为失败状态
    for item in items:
        if item.get("account") == test_account:
            assert item.get("status") != 1, \
                f"密码错误登录被错误记录为成功，日志详情: {item}"
            break
```

### 后续推荐
- 同时验证日志中 `message` 字段包含失败原因（如"密码错误"）
- 为"账号不存在"、"账号被禁用"等场景补充类似的日志内容校验
- 建立日志审计测试的断言标准，确保覆盖状态、消息、时间戳等关键字段

## 十、建议

1. 日志审计测试应覆盖日志记录的完整性和准确性，不仅验证 API 响应结构
2. 建立日志内容断言模板，统一各模块的日志验证标准
3. 为"成功登录"和"失败登录"分别建立基线数据，用于对比验证
4. 增加日志字段级别的断言：status、message、timestamp、account 等
