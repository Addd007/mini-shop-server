# Bug Report: Config 重复 Key 未被校验

**Bug ID**: BUG-CONFIG-DUP-001  
**标题**: POST `/cms/config` 传入重复 key 时未做唯一性校验，直接插入成功  
**模块**: 参数配置管理  
**严重级别**: 中  
**优先级**: P1  
**状态**: 已定位  
**发现日期**: 2026-06-15  
**提交人**: 测试团队 2号

---

## 一、问题概述

调用 `POST /cms/config` 新建参数配置时，传入已存在的 key（如 `"page_size"`），接口返回 HTTP 201 + `error_code: 1`（成功）。数据库中成功插入了重复 key 的记录。

Key 作为参数配置的唯一标识应具有唯一性约束——重复 key 会导致查询/更新时出现歧义，影响参数配置的可靠性。

---

## 二、影响范围

### 受影响功能
- 参数配置新建
- 按 Key 查询（`GET /cms/config/key/{key}` 可能返回多条记录中选择错误的）
- 按 Key 更新（`PUT /cms/config/key/{key}` 可能只更新其中一条）

### 受影响接口
- `POST /cms/config`
- `GET /cms/config/key/{key}`
- `PUT /cms/config/key/{key}`

### 业务影响
- 同一 key 存在多条记录，参数生效不确定
- 系统配置可能出现不可预测的行为（如 page_size 有多个值）
- 数据库数据污染

---

- 服务地址：`http://127.0.0.1:5000`
- 数据库：MySQL 8.4.9

### 步骤 1：获取管理员 Token
```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:5000/v1/token \
```

```bash
curl -s -X POST http://127.0.0.1:5000/cms/config \
  -H "Content-Type: application/json" -u "$TOKEN:132" \
  -d '{"name":"重复","key":"page_size","value":"20","type":true}'
```

### 步骤 3：查询列表验证

## 六、预期结果

接口应返回数据重复错误，提示"key 已存在"，不创建新记录。

---

## 七、根因分析

### 1. 现象分析
- `Config` 表的 `key` 字段未在数据库层面设置 UNIQUE 约束
- API 层和 DAO 层均未对 key 做重复性检查

### 2. 关键代码
- [app/api/cms/config.py](app/api/cms/config.py) — `create_config()` 方法
- [app/dao/config.py](app/dao/config.py) — 新建配置逻辑
- [app/models/config.py](app/models/config.py) — Config 模型定义

### 3. 根因结论

**`Config` 模型的 `key` 字段缺少数据库 UNIQUE 约束，且 API 层无应用级重复校验。** `key` 列定义为 `Column(String(64))` 无 `unique=True`。`POST /cms/config` 直接调用 `Config.create()` 写入，未调用 `Config.abort_repeat()` 做重复检查。

**关键代码定位**：
- `app/models/config.py:16`：`key = Column(String(64))` —— 缺少 `unique=True`
- `app/api/cms/config.py`：`create_config()` 未调用 `abort_repeat(key=...)`

---

## 八、修复方案

### 当前采取的修复策略
- **方案 1**：在 DAO 层增加 `key` 重复查询，发现重复返回错误
- **方案 2**：在数据库层面为 `config.key` 添加 UNIQUE 索引

### 后续推荐优化方向
- 数据库唯一约束 + API 校验双保险

## 十五、结论

该问题属于**数据唯一性校验缺失**。`config.key` 无数据库级和应用级唯一性保护。增加 UNIQUE 约束和 API 校验即可修复。
